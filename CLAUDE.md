# Sandfall

Shared classroom falling-sand game, hosted on GitHub Pages and synced through Firebase Realtime Database.

## Updating the live site

The `main` branch is the website. GitHub Pages republishes it within a minute or two of every push.

- Repo: https://github.com/Adrianshch/sandfall
- Site:
  - Cat Emotions cubbies (v6), three views by path (not hash):
    - student: https://adrianshch.github.io/sandfall/sandfall/ — source `sandfall/index.html`
    - class wall: https://adrianshch.github.io/sandfall/sandfall/display/ — source `sandfall/display/index.html`
    - admin: https://adrianshch.github.io/sandfall/sandfall/admin-cappy/ — source `sandfall/admin-cappy/index.html` (the user chose this path)
  - Cat Memories (v5 ball game, shared picture, `#play`/`#display`/`#teacher-CODE`): https://adrianshch.github.io/sandfall/cat-memories/ — source `cat-memories/index.html`. Keep it exactly as it is unless the user asks.
  - Cat Emotions Tube (v4, same hash modes): https://adrianshch.github.io/sandfall/slide.html
  - The v2 sand game that used to be at `sandfall/` was replaced by v6; it lives on as tag `v2`.
- The root `index.html` and `memories.html` only forward old links (keeping the `#...` part) to `sandfall/` and `cat-memories/`. Edit the pages in the folders, not these. `sandfall/` forwards an old `#display` or `#teacher...` hash to `display/`.
- Pages in folders load shared files with `../` (`../config.js`, `../images/...`); pages one level deeper use `../../config.js`. `sandfall/engine.js` finds the cat pictures from its own address.

After a change the user asked for: check it, commit with a short message, then `git push`. Then tell the user the site will update in a minute or two at the GitHub Pages address.

## Cat Memories ball game (`cat-memories/index.html`, page title "Cat Emotions"; was `memories.html`)

Glowing cat-memory marbles instead of sand. Sixteen cat balls on offer, coloured by the mood meter (pleasant + calm green, pleasant + energetic yellow, unpleasant + calm blue, unpleasant + energetic red; each ball its own shade within its family): a main row of five (`PICKER`: Happy, Sad, Scared, Confused, Calm) plus a More button that opens a scrollable side panel listing every cat, starters included, grouped under colour headings (`MORE_GROUPS`: yellow Happy, Excited, Curious, Silly, Hungry; green Calm, Chill, Focused; blue Sad, Confused, Bored, Tired; red Scared, Angry, Nervous, Upset). Panel copies of starter buttons get ids ending in `-more`. Worried (id 15) and Playful (id 13) are retired from the panel but stay in `MOODS` so old drops still draw. When adding a cat, pick its quadrant and a new shade in that family. Hungry uses a still frame of the tongue-out cat; Playful (id 13) used the same cat and is left out of the panel but kept in `MOODS` so old drops still draw. `MOODS` index is the colour id stored in drops, so never reorder or remove entries; add new ones at the end. Cat photos live in `images/cat-*.webp`: the cat is cut out of its photo with macOS Vision subject lifting (transparent background), then the face is cropped, bulged like seen through glass and cut to a circle. `paintMarble` fills behind the cat with a light wash of the ball's colour and adds edge shading and glints; the cat itself is not tinted. GitHub Pages lets browsers cache files for 10 minutes, so whenever a cat picture changes, bump `ASSET_V` in memories.html (image URLs carry `?v=ASSET_V`), and tell the user a hard refresh (Cmd+Shift+R) shows the update immediately. Calm uses the sleeping kitten because the user's preferred calm photos were watermarked. Drawn faces (`faceSvg`) remain available for any marble without a photo. Never use watermarked stock photos (Adobe Stock, Shutterstock, etc.), product photos, or professional photos of trademarked celebrity pets (e.g. Grumpy Cat) on the public site. Same modes (`memories.html#play`, `#display`, `#teacher-CODE`). Same sync design: ordered drop log, commit horizon, checkpoints and rollback. Marble settling (`settle`) must stay deterministic like sand placement: seeded `rng32`, plain arithmetic and `Math.sqrt` only. Marbles push each other (`simulate`): settled marbles sleep; moving ones fall, bounce and roll, and a hit harder than `WAKE_V` (scaled by weight, capped at 2x) wakes a sleeping marble so it gets knocked along. Moving pairs share pushes by weight, except a marble pinned against the floor or a wall doesn't give way (`shares`, `pinned`). After each event `playOut` repeats: wake marbles near spots where something left that lost support, simulate, pour loose sand, then a whole-box cleanup (`relaxAll`) pushes every overlapping pair apart, then any touching same-kind pair combines (`anyMerge`), until nothing changes. Merging (`place`, `findMerge`): when a marble comes to rest touching a same-kind marble, and a marble with their combined area (r = sqrt(r1^2 + r2^2), agar.io style) fits at their area-weighted centre or up to one radius above it without overlapping anything, the two are replaced by that bigger marble, which then rolls to rest. Marbles left unsupported then drop into the gap (`supported`: floor, two marbles below, or one below plus a wall), and anything that comes to rest is checked for merges again, so chains can happen. Balls have their own radius `r` and memory count `n`; the counter shows total memories. Popping (`pop`): a drop log entry with `l: 1` is a tap at `p`; it removes the smallest marble under that point and turns about half its area into sand (fine 1-unit grains in a 480x300 grid, `sand`; each pop's grains run light tint -> marble colour -> deep shade in soft wavy bands via `sandPalette`/`grainColour`, plain arithmetic only), scattered up to 1.2 radii and poured grain by grain (`pourGrain`) through open cells only, so sand never appears in sealed space. Marbles collide with sand grains, rest on them, and sand left hanging pours down (`pourLooseSand`). After anything is removed or moves, only marbles near that spot are rechecked for support (`dropLoose` with `gone` spots); never recheck every marble on every event (it was 5x slower). Checkpoints store the sand grid too. New drops have radius 18. Each live drop records a frame timeline (`makeTimeline`) for animation; replays don't animate. Checkpoints deep-copy balls because settling mutates them.

Its drops live in Firebase at `pours/c<gen>` (the earlier nine-colour marble test used `pours/m<gen>`) and its screens report modes `mplay`/`mdisplay`, so it works under the existing rules. Both pages share `state/gen`, so Start fresh on either page clears both.


### Memories: keeping it smooth (kids spam it)

- Drawing: settled marbles are drawn once into a cached layer (`layer`, rebuilt when `worldVersion`, `animsVersion` or the popping set changes); sand is a 240x150 canvas updated only when the world changes or grains are flying. Only moving/bursting marbles draw every frame. Keep it that way.
- Work per frame: replayed events run in full, new (animated) events stop after 8 ms of work per frame and continue next frame (`commit(frameStart)`).
- Each screen does at most one drop or pop every 350 ms (`ACTION_GAP`); faster taps are ignored on purpose.
- New events (never committed before) share an 8 ms budget per frame, including a big catch-up when a screen joins late; replays after a late arrival run in full so nothing flickers.
- A marble that appears in several overlapping animations is drawn once, from the newest.
- The dock shows `build YYYY-MM-DDx`; change it on every update so the user can check a screen has the latest version (GitHub Pages caches for 10 minutes).
- Pops carry the tapped marble's id (`t`) so they hit the marble the child saw, even mid-fall; the tapped marble starts bursting on that screen immediately (`popping`).
- Merging is immediate: `simulate` stops the moment two same-kind marbles touch (`lastHit`), they combine right away (6-frame animation), and marbles still moving carry on with their speed (`lastFlying`).
- No shivering: contacts slower than 1 unit/step don't bounce, and recorded motion is smoothed over 5 frames for display (`finish`).
- Taps: the whole glowing ball counts (radius x1.3 + 3); a tap on a ball that is still appearing does nothing.
- Touching same-kind marbles always combine (nearest open spot above, else dropped from the top; if the box is full they stay apart). After every roll the marble is pushed out of neighbours and, if still wedged, moved to the nearest clear spot in fixed directions; grains it was nudged into are moved over its top (`shiftSandOut`).
- Sand speed-ups (keep them): `markMarbles` stamps cells with a version and skips re-marking when a fingerprint of marble positions is unchanged (the fingerprint weights each marble differently and squares positions, because symmetric pushes keep plain sums equal); `sandTop` (top grain per column) and `patch` (grains per 8x8 patch) are kept up to date by `pourGrain`/`liftGrain` and rebuilt by `refreshSandTop` after rollback; `pourLooseSand(rand, spots)` only scans columns around spots where something moved, and every event ends with one whole-box sweep so no grain is left hanging.
- Physics tests live in the conversation scratchpad, not the repo; when changing physics, re-check that shuffled arrival orders give identical marbles and sand, and that nothing overlaps.

## Cat Emotions Tube (`slide.html`, v4)

Same cats, picker, sharing and modes as `memories.html`, but the world is a single-file queue in a winding tube. The shared state is only the order of the cats (`balls`, front first); positions come from `layout()` along the tube's centre line (`PATH`, `SLOTS`), so screens can't disagree. Adding pushes a cat at the back (ignored when `CAPACITY`, fixed at 70, is reached); popping removes it and everyone behind rolls forward one slot (a ripple in `makeTimeline().roll`). Popped sand is only a fading animation (`drawBursts`), not lasting sand. Its drops live at `pours/s<gen>`; screens report `splay`/`sdisplay`; Start fresh on any page clears it too. Build label `build YYYY-MM-DDtN`.

## Cat Emotions cubbies (v6: `sandfall/`)

The v5 cat ball game, one private picture per student.

- **Two modes** (v7): the start screen first asks "My own cubby" (single: private, username, everything below) or "Class colab". The colab is one shared cubby (`Cubbies.COLAB_ID`, a fixed 64-hex id = SHA-256 of `sandfall-colab`, so the cubby rules accept it) that anyone opens with no username and everyone plays in at once, synced like v5 (ordered drop log, horizon, rollback). Badge "class colab"; "Start fresh" (anyone, with a confirm) replaces "Delete my cubby": `clearColab` deletes the cubby and makes it again, and its new `made` time starts the new picture. `watchColab` tells every screen the current `made` (or null while it is being cleared, and makes the colab if it is missing); screens then reset and `follow(..., since = made)`, which leaves out drops and saved pictures older than `made`, so taps sent during a clear can't come back. In the colab a refused write is ignored if the colab restarted meanwhile. The status pill counts people in it (`screens/<session>` = `{mode: 'colab'}`, removed on disconnect). There is no way back to the start except refreshing, in either mode.
- **Student** (`sandfall/index.html`), own cubby: asks "I'm new" or "I've been here before", then a username. New + name already used: refused ("taken"). Returning + unknown name: a new cubby is made under that name (with a note). Inside the cubby there is no way back except refreshing, which always shows the start again (nothing is remembered in the browser). "Delete my cubby" (with a confirm dialog) deletes it; if the cubby disappears while open (deleted here, on another tablet, or by the admin), the page goes back to the start with a message. Usernames: NFKC, trimmed, spaces collapsed, lower case (`Cubbies.tidyName`).
- **Balls / Sand switch** (v7, `tool` in the student page, per tablet, starts on Balls): Balls is the v5 game. Sand: the canvas cursor is hidden and the chosen cat (`#pen`, a canvas drawn with `paintMarble`, about 1.7 x R wide, wiggles while pouring) follows the pointer; a finger shows it only while pressed. Holding pours sand like v2: every frame adds the pointer spot, every 100 ms (`POUR_MS`) the stretch is sent as one drop with `l: 2` (`l: 3` when it continues a stretch: its first point is the previous end and gets no sand), `r` = brush 3, `p` = the path `x,y,x,y,...` (at most 80 numbers). Taps in sand mode never pop. Engine `pourSand`: about r*r*0.7 grains per step, steps one brush apart, only into open cells (never inside a marble or the pile), poured with `pourGrain`; colour `grainColour(sandPalette(cat), tri(k / 6000), sparkle)`, so a long pour drifts through light, middle and deep bands. Marbles are not moved by poured sand. Sand drops wait only `SAND_HORIZON` (100 ms) before settling, balls still `HORIZON`. The animation lets each grain start falling in the frame its spot was touched (`tl.sand(grains, delay)`), so the stream looks continuous. Sand pours don't count as memories.
- **Display** (`display/`) and **admin** (`admin-cappy/`, `body data-wall="admin"`): both run `wall.js` + `wall.css`. The colab picture (captioned "Class colab", always shown, `COLAB_SCALE` 1.5 times a student tile or as big as fits) sits on the left, the student cubbies in a grid beside it (oldest first), all as big as fits (`layout` over the `#stage`); the whole class's cat bar has its own column on the right. Never show names (none are stored anyway). Admin: tap a student tile for Remove, or the colab for Start fresh; the dialog has a sharp preview and the memory count. Status pill shows "Catching up…" while any tile still has more than 2 drops waiting.
- **Class cat bar** (v7, `wall.js` `drawBar`, display and admin; it replaced the per-cubby bars): one canvas (`#classMix`) in the right-hand column, captioned "Whole class". A thick bar, bottom to top 0 to 100%, one solid block per cat sized by its share of the uses summed over every cubby and the colab; blocks stack in mood-meter energy order (`STACK`: Blue, Green, Yellow, Red families from `MORE_GROUPS`, retired cats last) so a cat keeps its place; hairlines between blocks; empty cubby = empty grey track. Each block has a cat-ball flag (cached sprite, `flagSprite`) on a stem in its colour, at the block's middle, spread apart so none overlap and shrunk if too many. Blocks ease to new sizes; while any tile is catching up the bar redraws at most every 300 ms. The column's `title` lists the percentages. Uses come from the engine: `world.uses()` counts one per marble dropped (`l: 0`) and one per press of sand (`l: 2`, not `l: 3`); pops don't count. The tally is kept in checkpoints and saved pictures (`SNAP_V` 2: `b` = `{m: marbles, u: uses}`; v1 pictures from v6 still load and count the memories they hold). 
- **Engine** (`engine.js`, `window.CatWorld`): the v5 physics, log, timeline and drawing code moved into `createWorld({canvas, checkpoints})` so one page can run many worlds. Behaviour must stay identical to v5 (all the v5 rules above apply: determinism, sand speed-ups, smoothness). Shared across worlds: MOODS, sprites per scale (`spritesFor`), the server clock (`nextKey`/`now`). A world skips drawing when nothing changed (`drawnKey`), which keeps a wall of 30 tiles cheap. The wall keeps 2 checkpoints per world (memory), the student 40.
- **Saved pictures**: `world.savedState(before)` returns the newest checkpoint whose drops are all older than `before`; `startFrom(state)` starts a world from one (drops up to `upto` are ignored, rollbacks go back to it). `packState`/`unpackState` store it as `{v, k, i, n, b: marbles (and uses) JSON, s: sand deflated + base64}` (about 50 to 160 KB). The student's tablet saves one (`Cubbies.makeSaver`) once 40 more drops have settled, at most every 30 s, only after it has caught up, only from drops at least 10 s old, and again when the page is hidden. Screens read the picture once, then only drops from its `k` onward (`orderByChild('k').startAt`). Browsers without CompressionStream skip saved pictures and replay everything. Replaying costs about 10 ms per drop, so without saved pictures 25 cubbies x 150 drops take about 35 s to fill the wall.
- **Firebase** (`cubbies.js`, `window.Cubbies`): `cubbies/<id>` = `{made}` (the wall watches this list), `drops/<id>/<drop>` = the v5 drop records, `snaps/<id>` = the saved picture. `<id>` = SHA-256 hex of `'sandfall-cubby:' + tidyName(username)`, so the database never holds a name. Deleting a cubby removes all three in one `update`. The rules for these three paths are in README.md (v6 setup); v7 raised the `drops` `p` limit from 16 to 400 characters for sand paths. The user adds them inside their existing rules (which hold the teacher code and aren't in the repo), so give them a block to paste, not a whole rules file. If those rules change, give the user the new block and say exactly what to replace.
- The build label is `v7 · build YYYY-MM-DDx` in all three pages; scripts and CSS load with `?v=` the same date, so bump both on every change (GitHub Pages caches for 10 minutes).
- Testing (scratchpad, not the repo): a fake Firebase (`fakefirebase.js`, shared between tabs through localStorage; fine for one writer at a time, but it loses simultaneous writes, so the colab test uses `fakefirebase2.js` + `fakeserver.js`, one store in the test runner that enforces the cubby rules) served by Playwright in place of the gstatic scripts, plus Node checks that the engine matches v5 exactly and that saved pictures plus later drops equal a full replay. The real database isn't reachable from the cloud container.

## Things that must stay true

- Cat Memories and the Tube take their mode from the URL hash: `#play` (default), `#display`, `#teacher-CODE` (display plus Start fresh).
- v6 cubbies take their view from the path (`sandfall/`, `sandfall/display/`, `sandfall/admin-cappy/`), never the hash.
- Every screen must compute the identical picture. Pour placement (`settle`, `pourAt`, `walk`, `applyChunk`) must use only the seeded `rng32` and plain arithmetic: no `Math.random`, `Math.sin`, `Math.cos` or `Math.hypot` there. Changing the grid size (480x300), the pour format or placement rules changes the picture for everyone; old pours in Firebase will replay differently, so suggest Start fresh after such a change.
- Cosmetic falling particles may use `Math.random`.
